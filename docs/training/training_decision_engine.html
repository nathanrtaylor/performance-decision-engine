Training Decision Engine

Extending the coaching engine's methodology to new-hire training — as remediation routing that tells an expert exactly what to retake, and stays quiet when they're on track.

Phases 0–2 complete Phase 3 next branch training-insights updated 2026-09-01

01 What it is

The Training Decision Engine extends the Coaching Decision Engine's methodology — weight data → find signals → summarize → recommend — from live-call coaching to new-hire / expert training.

Its goal is remediation routing: for each expert, surface which specific parts of their training to go back and retake — targeted at the skills where they're deficient. When nothing is materially deficient, no remediation is prescribed.

The output is a governed, per-expert remediation plan (what to retake, why, with the progression gate) plus a training dashboard — engine-generated and evidence-backed, not hand-written.

The remediation model — three properties that drive the design

  • Block-gated trigger. Training is organized into sequential learning blocks, each ending in a test call. Scoring below the acceptable threshold on that test call triggers remediation for the block: retake the block's skill-level simulations (for the deficient skills) and the end-of-block test call, and the expert can't progress until the gate clears.
  • Steerable scope. We can tune how far back to send an expert (this block / back N blocks / to the block that first taught a weak skill) and what areas (which modalities and skills) — via config, without code changes.
  • Once-only. An expert is never sent back to remediate material they've already remediated; a remediation-history exclusion keeps plans from looping.

02 Architecture — reusing the coaching engine

The core finding from exploration: ~70–80% of the analytical engine is domain-generic (percentile scoring, temporal windowing, evidence gating, prioritization, three-tier selection), and most of the rest is pure YAML config. Coaching-specific behavior is concentrated in ingestion, a shallow org-enrichment block, narrative text, and dashboards.

So training is an additive, parallel domain: it reuses the shared src/cde core unchanged and runs from its own governed config set (configs/training/). The live-call coaching pipeline is untouched.

Training data (tall-skinny)                Shared engine (UNCHANGED)
  TrAIning Assist skills ─┐
  CBT completion/scores  ─┼─→ build_signals → thresholds → temporal window →
                          │    scoring (percentile-of-deficit) → prioritization →
                          │    three-tier selection → abstention → receipts
  configs/training/ (isolated) drives every metric / benchmark / topic / threshold

Two data sources (not three)

  1. TrAIning Assist (AI simulator): per-behavior behaviorPresent flags → rolled up to skill-level pass-rates; also the source of end-of-block test calls.
  2. Computer-Based Training (CBT) (Workday Learning): course completion + scores. The CBT score is the assessment — there is no separate assessments feed.

Both conform to the engine's tall-skinny contract — (agent_id, period, call_type, metric_key, numerator, denominator, calc) — valued as a 0–1 pass-rate (value = calc), exactly like the coaching behavior_scores source.

Temporal grain = DAY

Training progresses day-by-day, so the domain runs on a daily grain. This is a config-level change, not a core rewrite: windowing selects the last N distinct period values (period-generic, not 7-day-calendar math) and trend runs over real timestamps. Binding period to the event day + a day-unit temporal: block makes the whole pipeline day-grained, with a rolling last-N-days window (currently 30). The internal score columns keep their weekly-era names (level_8w); the values are day-based.

05 Proposed training_program.yaml schema

Phase 3's crux is the program structure, which you define incrementally. It's a config you fill in a block at a time; the engine runs on whatever's defined and a checker reports what's still missing. Below is the proposed schema (empty scaffold + field docs) — please sanity-check the shape before we build program.py against it.

Seeded from the ASCEND strategy doc

A 16-block instance now exists at configs/training/training_program.yaml — blocks, order, labels, assessment methods, simulation counts, gates at pass_mark: 0.90, and best-effort develops: mappings (all 22 cataloged skills covered). It adds pacing dimensions on top of the schema below: per-block estimated_hours and expected_completion_day (days since training start, derived from cumulative hours at a program-level pace.hours_per_day knob — provisional until the real class calendar replaces it). gate.test_call refs, component (CBT/sim) enumeration, and the tools/troubleshooting skill mappings remain TODO.

program:
  name: "<program name>"
  blocks:                          # in the order an expert progresses
    - id: block_1                  # stable id used by program.py + receipts
      label: "<human label>"
      order: 1
      gate:                        # end-of-block TEST CALL that gates progression
        test_call: "<challenge_id / test-call key in the data>"
        pass_mark: 0.80            # optional; falls back to a default
      components:                  # remediable items; each names the skills it develops
        - kind: skill_sim          # a TrAIning Assist scenario
          ref: "<challenge_id>"
          develops: [ "<skill_id>", "<skill_id>" ]
        - kind: cbt                # a Workday Learning course (score = assessment)
          ref: "<courseid>"
          develops: [ "<skill_id>" ]
    # - id: block_2 ...            # add blocks as you define them
  defaults:
    gate_pass_mark: 0.80
  • develops: is the routing table in inverse form (component → skills). program.py derives the forward map (deficient skill → components to retake) from it, so the config stays in natural "here's what this course/sim teaches" phrasing.
  • Partial is fine. Unmapped skills, courses not tied to a block, or a block missing a gate are reported as TODO by the checker — not errors. The engine remediates only where structure is defined.
  • Skill ids are the ones already cataloged (warm_greeting, account_assessment, …); CBT ref is the courseid; sim ref is the challenge_id.

Companion — remediation.yaml (steerable policy)

remediation:
  gate_pass_mark: 0.80             # acceptable performance on a block-gate test call
  scope:
    how_far_back: current_block    # current_block | back_n | to_skill_origin
    back_n: 1
    include_modalities: [ skill_sim, test_call ]
    skills: deficient_only         # deficient_only | whole_block
  once_only: true                  # never re-prescribe already-remediated material

07 Assumptions to confirm & open items

CBT assumptions — confirm on the first real extract

Each is a one-line SQL change, flagged in training_cbt.sql.j2:

• userid is the numeric employee id (so CBT joins TrAIning Assist on agent_id). If it's a username, we add a userid → employee_id map.
• score is on a 0–100 scale (normalized /100). If already 0–1, drop the /100.

Reconciliation gaps (SME review)

  • 3 sim behaviors have no skill mapping and are dropped: ask to enroll, celebrate enrollment, disclosures statement.
  • 11 challenge_ids in the data aren't in training_profiles.yaml (likely newer/test profiles); their rows are dropped until reconciled.

Benchmark calibration

A flat 80% pass-mark misfits some skills — e.g. resolve_concerns never dips below 0.83, so nobody is ever "deficient" on it. Tune per-skill pass-marks with the benchmark-recalc module against real daily data.

Program structure

The biggest open item — blocks, components, gates, and skill mappings (Section 5) — is the domain/SME definition currently in progress.

08 How to run (today)

# 1. Extract training data (needs DB access) -> data/raw/adhoc/latest/
python extraction/scripts/run_extract.py --config extraction/configs/extract_training_assist.yaml

# 2. Roll TrAIning Assist behaviors up to skill pass-rates
python -m cde.cli.build_training_assist_skills --raw-dir data/raw/adhoc/latest

# 3. (Re)generate the mechanical training configs from the real data
python tools/gen_training_configs.py --raw-dir data/raw/adhoc/latest

# 4. Validate config integrity
python -m cde.cli.check_config --configs-dir configs/training --raw-dir data/raw/adhoc/latest

# 5. Run the training domain through the shared engine
python -m cde.cli.run_pipeline --configs-dir configs/training \
    --raw-dir data/raw/adhoc/latest --out-dir outputs/training_runs/<date>

A dedicated run_training_pipeline entrypoint + training dashboard arrive in Phase 4.

10 Guiding principle

The system should not slow leaders down. It should make fast decisions work on purpose.

For training: the moment an expert falls short at a block gate, the engine names exactly what to retake and why — and stays quiet for everyone who's on track.
